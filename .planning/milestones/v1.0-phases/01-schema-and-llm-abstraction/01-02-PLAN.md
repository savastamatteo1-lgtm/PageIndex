Create `pageindex/llm/provider.py` with the `LLMProvider` class:
- Constructor takes a `config: dict` with keys: `completion_model` (str), `embedding_model` (str), `embedding_dimensions` (int, default 768), `temperature` (float, default 0).
- `complete(messages: list[dict], **kwargs) -> str`: Calls `litellm.completion()` with `model=self.completion_model`, `messages=messages`, `temperature=kwargs.get("temperature", self.temperature)`. Returns `response.choices[0].message.content`.
- `acomplete(messages: list[dict], **kwargs) -> str`: Async version using `litellm.acompletion()`. Same signature and return.
- `embed(texts: list[str]) -> list[list[float]]`: Calls `litellm.embedding()` with `model=self.embedding_model`, `input=texts`, `dimensions=self.embedding_dimensions`. Returns `[item["embedding"] for item in response.data]`.
- `aembed(texts: list[str]) -> list[list[float]]`: Async version using `litellm.aembedding()`. Same signature and return.
- `count_tokens(text: str, model: str | None = None) -> int`: Calls `litellm.token_counter()` with the completion model. Returns token count.

IMPORTANT: Use `gemini/` prefix in model names for Google AI Studio routing (not Vertex AI). LiteLLM reads `GEMINI_API_KEY` from environment for Gemini models. Set `litellm.drop_params = True` at module level to prevent errors from unsupported params across providers.

Also add a module-level convenience function `get_provider() -> LLMProvider` that creates a singleton provider instance from `load_llm_config()`. This is used by utils.py backward compat and can be used by new code that doesn't want to manage config explicitly.

Create `pageindex/llm/config.py`:
- `load_llm_config() -> dict`: Loads config from `pageindex/config.yaml`, extracts the `llm` section. Returns dict with `completion_model`, `embedding_model`, `embedding_dimensions`, `temperature`. Falls back to sensible defaults (gemini/gemini-2.0-flash, gemini/gemini-embedding-001, 768, 0) if keys are missing.
- Uses the existing `ConfigLoader` pattern from utils.py -- find the config.yaml relative to the package directory using `Path(__file__).parent.parent / "config.yaml"`.

Strategy: Keep the `google-genai` direct SDK as the INTERNAL implementation for the existing functions in this phase. The reason is that `Gemini_API_with_finish_reason` returns finish_reason metadata that LiteLLM's standard completion does not directly expose in the same way, and `page_index.py` depends on this exact behavior for handling MAX_TOKENS truncation and retry logic. A full migration would risk breaking the complex tree-indexing flow.

What to change:
1. Add an import of `LLMProvider` and `get_provider` from `pageindex.llm.provider` at the top of the file (lazy import to avoid circular dependencies -- import inside function bodies if needed).
2. Refactor `count_tokens` to delegate to `LLMProvider.count_tokens()` with a fallback to the existing google-genai implementation if the provider is not available. This is safe because token counting has no side effects.
3. Add a NEW convenience function `llm_complete(messages: list[dict], **kwargs) -> str` that calls `get_provider().complete(messages, **kwargs)`. This is the recommended entry point for NEW code in subsequent phases. It does NOT replace existing Gemini_API functions.
4. Add a NEW convenience function `llm_embed(texts: list[str]) -> list[list[float]]` that calls `get_provider().embed(texts)`. This is the recommended entry point for embedding calls in subsequent phases.
5. Leave `Gemini_API`, `Gemini_API_async`, `Gemini_API_with_finish_reason`, `ChatGPT_API`, `ChatGPT_API_async` UNCHANGED in this phase. They continue using `google-genai` directly. Deprecation and full migration to LiteLLM is a future concern (not in scope for Phase 1).

Add a module-level docstring update noting that new code should use `llm_complete()` and `llm_embed()` instead of the legacy `Gemini_API`/`ChatGPT_API` functions.

  <action>
    **Prompt templates (`prompts.py`):**

    1. `build_metadata_extraction_prompt(vocabulary: dict) -> str`:
       Build a system prompt for Italian legal metadata extraction. The prompt MUST:
       - Instruct the LLM to extract: doc_type, date (ISO 8601 format), authority, ecli, gu_number, legal_area (array), parties (array of {name, role}), court_level, cross_references (array of {ref, type})
       - Inject the full vocabulary dict (doc_types, legal_areas, court_levels, party_roles, cross_reference_types from legal_vocabulary.yaml) so the LLM uses consistent terminology
       - Instruct to return null for fields that cannot be determined from the text
       - Be in Italian context (the documents are Italian legal texts)
       - Tell the LLM: "You are analyzing an Italian legal document. Extract structured metadata from the text provided."

    2. `build_description_prompt() -> str`:
       Build a system prompt for one-sentence document description generation. Instruct: "Generate a single, concise sentence that describes what this Italian legal document is about and what distinguishes it from other documents. Focus on the subject matter, parties involved, and legal outcome."

    3. `METADATA_JSON_SCHEMA: dict`:
       Define the JSON schema dict for use with LiteLLM `response_format`. Structure matching the metadata fields above. Use `{"type": ["string", "null"]}` for optional string fields. Use `{"type": "array", ...}` for legal_area, parties, cross_references. Set `"additionalProperties": false` and `"strict": true`.

    4. `load_vocabulary() -> dict`:
       Load `pageindex/schema/legal_vocabulary.yaml` using pathlib to resolve the path relative to the package root (use `Path(__file__).resolve().parent.parent / "schema" / "legal_vocabulary.yaml"`). Cache the result at module level to avoid repeated disk reads.

    **Recursive text splitter (`chunker.py`):**

    1. `chunk_leaf_nodes(leaf_nodes: list[dict], page_list_or_pdf_path, tree_json: dict, max_tokens: int = 800, overlap_ratio: float = 0.1, count_tokens_fn=None) -> list[ChunkData]`:
       - Iterate over leaf nodes from `get_leaf_nodes()`
       - For each leaf node, get its text. If the leaf node has a `text` field (when `if_add_node_text='yes'`), use it directly. Otherwise, extract text from the PDF using `get_text_of_pages(pdf_path, leaf['start_index'], leaf['end_index'], tag=False)` as fallback
       - Build the tree path string by traversing the tree_json from root to the leaf's node_id (e.g., "Article 4 > Section 2 > Paragraph 3"). Implement `build_tree_path(tree_json, node_id) -> str` helper for this
       - If token count of leaf text <= max_tokens, create a single ChunkData
       - If token count > max_tokens, call `recursive_split()` to get sub-chunks, then create ChunkData for each with sub_chunk_index
       - The `count_tokens_fn` parameter should accept a callable `(str) -> int`. If None, raise ValueError with message "count_tokens_fn is required"

    2. `recursive_split(text: str, max_tokens: int, overlap_ratio: float, count_tokens_fn) -> list[str]`:
       - Implement the hand-rolled recursive splitter per RESEARCH.md pattern
       - Separators hierarchy: `["\n\n", "\n", ". ", " "]` (paragraphs -> lines -> sentences -> words)
       - For each separator level, split text and greedily accumulate segments until exceeding max_tokens, then start a new chunk
       - Add overlap between consecutive chunks using `_add_overlap()` helper
       - Fallback: if no separator works (very long text with no whitespace), split at midpoint and recurse

    3. `build_tree_path(tree_json: dict | list, target_node_id: str) -> str`:
       - DFS through tree_json to find the path from root to the node with `node_id == target_node_id`
       - Return path as " > " separated string of node titles
       - If node_id not found, return empty string

    4. `build_embedding_text(chunk: ChunkData, doc_metadata: dict) -> str`:
       - Build the full text for embedding: `[metadata block]\n\nSection: {tree_path}\n\n{chunk content}`
       - Metadata block includes: Title, Type, Date, Court, Legal Area, ECLI, Description
       - Per CONTEXT.md decision: every chunk gets the full metadata + tree path prefix before embedding
  </action>
